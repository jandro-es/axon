| 10 | ~~LOW~~ | **SHIPPED in v1.5.0.** Was: **`axon start`'s early refusals return before `deps.close()` is deferred.** Every other `loadProfileDeps` caller defers the close on the next line; `start` alone registers it inside the later shutdown-ordering closure (cancel → `wg.Wait()` → `bus.Close()` → `deps.close()` — that order exists so the dashboard/persister goroutines never race a closed DB). Three refusals return in the gap — `ValidateRecipes` (FR-201), `checkNotRoot`, `checkNotRunning` — each leaking the open SQLite handle (and, when built, the `fm serve` supervisor). **No practical impact:** the process exits immediately and the OS reclaims everything; the cost is in-process callers (cmd tests) leaking a handle per refused start, plus a pattern that reads as an oversight. **Fixed exactly as scoped:** a plain `defer deps.close()` right after the load, closure untouched. Defers are LIFO, so it runs *after* the shutdown closure — that ordering is preserved — and the second close is a no-op (`FMSupervisor.Stop` nils `proc` under its mutex; `sql.DB.Close` is idempotent). Regression test `TestStartRefusalClosesDeps` (`cmd/axon/start_cleanup_test.go`) drives a real refusal in-process and fails if the DB handle survives; `loadProfileDeps` became a func variable so a test can observe the deps a command builds. Happy path re-verified live: bind → run → SIGTERM → clean exit, pidfile removed. |
| 11 | ~~MED~~ | **FIXED on `main` (2026-08-21, released in v1.7.0).** Was: **the updater never told upgraders about new automations.** `config_missing_keys` scans `^ {0,4}[a-z_][a-z0-9_]*:` — no hyphens, 4-space indent cap — so it could not see `automations.<name>` entries, which are indented six and hyphenated. Verified empirically against a simulated 1.5.0 config: empty output. This mattered because `Schedulables()` iterates the *user's configured* automations map, so an automation with no entry is never scheduled, while `axon automations` renders it as "disabled" — which reads as *off* rather than *absent*. ISSUES #1's failure mode (registered but unschedulable) reappearing for upgraders instead of fresh installs. **Fixed** with `config_missing_automations`, which asks the new binary for its names via `automations --json` (authoritative — no example-file parsing, no indentation guessing) and lists any the config lacks; advisory only, never mutates the config, silent when binary/config/JSON are unusable. Wired into both updaters. |
| 12 | ~~LOW~~ | **FIXED on `main` (2026-08-21, released in v1.7.0)** — found while fixing #11. `update-macos.sh` ended with `[ -n "$NEW_KEYS" ] && info …`; under `set -euo pipefail` a false test makes that list's non-zero status the **script's** exit status, so a clean update with no new config settings exited **1**. Any scripted or CI use would have read a successful update as a failure. Both updaters now end with an explicit `exit 0` and a comment explaining why. |

## Process

- New findings append here with the same fields; sweeps update the header date.
- An issue leaves this file only by shipping (link the release) or by being
  explicitly declined (record why, as #7/#9 do).
- HIGH items should be dispositioned before the next feature slice starts;
  they are small on purpose.
